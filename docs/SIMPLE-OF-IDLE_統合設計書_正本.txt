# Simple-Of-Idle 統合設計書（正本）

## 0. ChatGPTへの作業指示

SOIの作業では、**最新GitHub `main`・この設計書全文・最新mainの実コード・現行UI・実際のruntime接続を確認した結果だけを根拠とする。**

この章は、ChatGPTがSOIの調査・設計・実装・設計書更新を行う際の**単一の作業プロトコル**である。

ChatGPTは、この章に記載された作業順序・禁止事項・判断基準を、GitHub API等のツール上の都合によって別の方法へ置き換えてはならない。

---

### 0.1 最上位原則

SOIの現在仕様は `docs/SIMPLE-OF-IDLE_統合設計書_正本.txt` を唯一の正本とする。

作業開始時に、必ず以下を最新mainから確認する。

1. 最新GitHub `main`
2. `docs/SIMPLE-OF-IDLE_統合設計書_正本.txt` 全文
3. 対象仕様
4. 最新mainの関連コード
5. 現行UI
6. UI → イベント → ハンドラ → 実処理 → データ更新 → 保存 → 再描画のruntime経路
7. 同じ責務を持つ既存実装
8. 旧実装・重複実装・競合実装・不要な旧入口
9. ファイル間の呼び出し・データ・責務の接続

過去の会話、過去のZIP、過去の設計書、過去のコード断片、過去の確認結果、過去mainの状態を現在状態の根拠として使用しない。

---

### 0.2 ChatGPTとTermuxの責務分離

ChatGPTの役割は、

- 最新mainの確認
- 設計書全文の理解
- リポジトリの再帰的・網羅的確認
- runtime経路の追跡
- 変更対象の特定
- 実装方針の確定
- Termuxで実行するための正確な変更手順の作成
- 実行結果の確認
- PUSH後のGitHub main再監査

とする。

実際のファイル変更・commit・pushはTermuxで行う。

ChatGPTはGitHubへ直接、

- ファイル更新
- commit
- push
- ブランチ更新

を行う運用にしない。

GitHub APIやその他のツールに直接書き込める機能が存在しても、それをSOIの通常実装経路へ変更してはならない。

**ツールの制約や利便性を理由に、この責務分担を変更してはならない。**

---

### 0.3 実装開始前の必須順序

実装を開始する場合、次の順序を変更しない。

`最新main確認`
→ `docs/SIMPLE-OF-IDLE_統合設計書_正本.txt全文確認`
→ `第0章の作業規則確認`
→ `対象仕様確認`
→ `リポジトリ再帰・網羅確認`
→ `関連コード確認`
→ `UI確認`
→ `runtime経路確認`
→ `既存・旧・重複・競合実装確認`
→ `変更対象確定`
→ `実装方法確定`
→ `Termux実行手順作成`

設計書全文を読まずに対象コードだけを見て実装方針を決定してはならない。

対象コードだけを見て設計書全体との整合性を判定してはならない。

---

### 0.4 PUSH前の最新main同期

PUSHを伴う変更では、Termuxで必ず最初に、

`git pull --ff-only origin main`

を実行する。

その後、同期された最新ローカル状態を基準に編集する。

作業指示で提示する基本順序は、

`git pull --ff-only origin main`
→ `編集`
→ `git add`
→ `git commit`
→ `git push origin main`

とする。

**PUSH前にユーザーへ確認作業を要求する工程を入れない。**

ChatGPTが作業指示として提示するコマンドは、編集からcommit・PUSHまで必要な工程を一つながりで実行できる形にする。

独立した実装課題は、一回の実装バッチにつき原則2件までとする。同一原因の関連修正、UI/runtime接続、回帰防止、正本設計書への仕様統合は、その実装課題に直接必要な範囲で同じ課題へ含める。独立した3件目以降の機能を同じバッチへ追加せず、次のバッチへ分ける。

過去に取得したローカル状態、過去の会話、以前の確認結果を現在mainの代わりに使用しない。

PUSH前の検証結果や確認結果だけを理由にPUSHを中止する手順を組み込まない。

PUSH後にChatGPTが最新GitHub `main`を再取得し、リポジトリと設計書を確認・監査する。

---

### 0.5 SHによる更新禁止

SOIの実装・設計書更新を、更新用の`.sh`スクリプトへまとめて実行する方式は使用しない。

Termuxでのファイル更新が必要な場合は、直接実行するPython等を使用し、実際の最新ファイル内容を読み込んでから変更する。

更新用スクリプトを別ファイルとして作成し、そのスクリプトを後から実行させる方式へ勝手に変更しない。

`/tmp`も使用しない。

ユーザーにファイルを手作業で編集させない。

**編集作業の提示方法：**
実際のファイル編集が必要な場合、ChatGPTは「編集済み」と扱わず、Termuxでそのまま実行できる**編集コマンド**を提示する。

編集コマンドは、最新mainへ `git pull --ff-only origin main` を行ったローカル状態を基準に、対象ファイルを読み込み、確認済みの編集アンカーだけを変更するものとする。

編集対象が `docs/SIMPLE-OF-IDLE_統合設計書_正本.txt` の場合も、同じくTermuxで実行できる編集コマンドとして提示する。

編集コマンドには、対象アンカーの存在数を確認し、0件または複数件の場合は推測編集せず失敗する処理を含める。

ChatGPT側でGitHubへ直接ファイルを書き込んだり、ChatGPT側でcommit・pushしたりする方式へ変更しない。

編集コマンドを提示しただけでは編集済みとは判定しない。

編集・commit・PUSHを実行するための作業指示は、必要な工程を一つながりのTermuxコマンドとして提示する。

ユーザー側でPUSH前の確認工程を挟ませず、PUSH後にChatGPTが最新GitHub `main`を再取得して実際の反映状態を確認する。

---

### 0.6 設計書全文の理解

`docs/SIMPLE-OF-IDLE_統合設計書_正本.txt`は一部を参照する資料ではなく、SOI全体を定義する一つの設計書として扱う。

変更対象が特定システムの仕様であっても、その章だけを見て実装を決定してはならない。

少なくとも、

- 全文
- 第0章の作業規則
- 対象仕様
- 関連するコード責務
- UI仕様
- runtime仕様
- 保存仕様
- renderer仕様
- 監査・検証仕様
- 非採用仕様

まで関連性を確認する。

設計書の一部とコードの一部だけが一致していることを、全体整合性の根拠にしない。

---

### 0.7 推測禁止

最新mainで実在を確認していないものを、編集対象として推測してはならない。

対象には以下を含む。

- ファイル
- 関数
- 関数境界
- 変数
- DOM
- ID
- class
- データ構造
- プロパティ
- renderer API
- script読み込み順
- runtime経路
- 設計書の文面
- SVG・画像・manifest

過去に存在したことだけを根拠に現在存在すると判断しない。

「おそらく」「以前は」「通常なら」「同じ構造なら」といった推測で編集対象を決めない。

---

### 0.8 編集アンカーの確定

編集対象は、最新mainの実コードを確認した結果だけから確定する。

編集対象を確定する前に、必ず次を確認する。

- 正確なファイル
- 正確な見出し
- 正確な関数
- 正確な変数
- 正確なデータ構造
- 正確なDOM
- 正確なイベント
- 前後の実コード
- 所属する責務
- 呼び出し元
- 呼び出し先
- UIからruntimeまでの接続

### 編集コマンド作成直前の再照合

実装調査時に確認したコードを、そのまま編集コマンドの根拠として再利用してはならない。

編集コマンドを作成する直前に、最新mainから取得した実コードと、実際に編集するローカル対象を再照合する。

必ず、

`GitHub最新mainの実コード`
→ `編集対象として特定した正確なコード`
→ `編集コマンドが置換する正確なコード`
→ `置換後に成立するコード`

を順番に確認する。

特に、関数全体・イベントハンドラ・HTML生成ブロック・設計書文面など、複数行を置換する場合は、調査時に見たコードと編集コマンドのアンカーが完全に同一であることを確認する。

「同じ処理のはず」「以前確認したコードと同じ」「構造から考えて存在するはず」といった理由でアンカーを作成してはならない。

### アンカー件数

編集コマンドは、実際に置換するアンカーについて件数を確認する。

- 0件 → 編集しない
- 1件 → そのアンカーを編集対象として確定
- 2件以上 → 文脈と責務を再調査し、対象を特定できるまで編集しない

アンカー件数だけでなく、アンカーの前後にあるコードが想定した対象と一致することも確認する。

調査時に存在した文字列が、編集時には存在しない場合は、別の文字列を推測して置換してはならない。

調査時に確認した構造と編集時の構造が異なる場合は、編集コマンドを作り直す。

単純な文字列出現数だけで編集対象を決定しない。

アンカーが存在しない場合、別のアンカーを推測して編集を続けない。

アンカーが複数存在する場合、周辺文脈と責務を確認せず一括置換しない。

編集コマンドそのものが最新mainの実コードと一致することを確認してから、ユーザーへ実行コマンドを提示する。
### 編集アンカーの再構成禁止
編集対象のアンカーは、記憶・推測・過去会話・過去main・断片的な検索結果から再構成してはならない。
編集アンカーは、編集コマンドを作成する直前に確認した最新mainの実コードから、そのまま連続して取得した本文を使用する。
複数行アンカーについて、最新mainに存在する複数の断片をChatGPTが結合したり、空白・改行・インデントを推測して組み立てたりしてはならない。
old = の置換文字列を使用する場合、その文字列全体が編集コマンド作成直前に取得した最新mainの連続本文と完全一致していなければならない。
Termux側ではgit pull --ff-only origin main後に同じアンカーを再検索し、0件なら編集せず再調査、1件なら編集対象確定、2件以上なら文脈と責務を再調査してから編集する。
調査時に存在したアンカーが編集時に存在しない場合、別の文字列へ置換してはならない。最新mainを再取得して実コードからアンカーを取り直す。
編集コマンドのPython構文・引用符・文字列境界も、提示前に成立することを確認し、編集対象本文そのものと編集コマンドの構文を混同しない。

### 作業手順の実行と独自判断の禁止
この第0章は確認用の参考資料ではなく、SOI作業を実行するときに必ず適用する実行手順である。

「作業手順を読んだ」「作業手順の内容を確認した」だけでは、作業手順を実行したとは扱わない。
実装・設計書更新・調査・編集コマンド作成では、第0章に定めた工程を実際の作業として順番どおり実行する。

ChatGPTは、第0章に定められている工程・判断基準・禁止事項を、自分の都合による別の手順・独自の検証方法・独自の判断基準へ置き換えてはならない。

特に、以下を禁止する。

- 作業手順にない工程を、作業手順より優先して追加しない。
- 作業手順にない判断基準を、既存の判断基準より優先しない。
- 「安全のため」「確実にするため」「同じ状態を再現するため」などの理由で、作業手順と異なる方式へ勝手に変更しない。
- 調査時点のHEAD、blob SHA、ファイル内容、アンカー、コード断片、判断結果を、編集時点の最新状態として固定しない。
- 過去に確認したHEADや過去mainの識別情報を、編集コマンドの検証値として固定しない。
- 調査時に確認したコードを、編集直前の再照合なしに編集コマンドへ流用しない。
- 「確認したから実行した」と扱わない。
- 「手順上はAだが、今回はBのほうが安全」といったChatGPT独自の判断で手順を変更しない。
- 手順にない停止条件を勝手に追加してPUSHや修正を中止しない。
- 手順にない代替編集方法、別のGitHub書き込み経路、別の検証方式へ勝手に切り替えない。

### 最新状態の扱い
最新mainは、その作業工程の直前に取得した状態を基準とする。

調査開始時に取得したHEADは、編集時の基準として固定してはならない。
編集コマンドを作成する直前に、最新mainと実際の対象ファイルを再取得・再照合する。

したがって、編集コマンド内へ調査時点のHEADを固定値として埋め込み、それと現在のHEADが一致することを編集条件にする方式は使用しない。

現在HEADが変化していた場合、それ自体を異常として扱わない。
最新mainを基準に対象コード・アンカー・周辺文脈を再確認し、最新状態から編集コマンドを作り直す。

### 確認工程と実行工程の区別
各工程について、以下を明確に区別する。

- 「確認した」＝対象の存在・内容・接続を調査した状態
- 「手順を実行した」＝第0章に定められた工程を実際にその順序で実施した状態
- 「編集した」＝Termux上で実際にファイルを変更した状態
- 「commitした」＝Git commitが作成された状態
- 「PUSHした」＝`git push origin main` が実行された状態
- 「実装完了」＝PUSH後の最新GitHub mainで設計書・コード・UI・runtime・保存・再描画・旧実装まで再監査して成立した状態

これらを同一視してはならない。

特に、設計書を読んだだけで「作業手順を実行した」と判定してはならない。
また、編集コマンドを提示しただけで「編集した」と判定してはならない。

### 作業手順からの逸脱防止

#### 二段階実行（Phase A / Phase B）

SOIの実装・設計書更新・調査作業は、必ずPhase AとPhase Bの二段階で実行する。

**Phase A：証拠収集・確定**

Phase Aは、実装・設計書編集・編集コマンドの提示を開始する前に、作業の根拠と実行可能性を確定するための必須工程である。

Phase Aでは、まだユーザーへ編集コマンドを提示してはならない。

Phase Aは「調査した」だけでは完了しない。以下の全項目を実際に確認し、最後に**ユーザーへ提示する最終コマンドそのもの**まで検証して初めて完了とする。

1. 最新GitHub `main`
2. `docs/SIMPLE-OF-IDLE_統合設計書_正本.txt` 全文
3. 第0章の現行作業手順
4. 関連する現行コード
5. UI・イベント・runtime接続
6. 既存・旧・重複・競合実装
7. 編集対象の現在の構造・出現数・責務
8. 編集方法の根拠
9. 編集コマンド作成直前の最新mainとの再照合
10. **実際にユーザーへ提示する最終編集コマンド全体の構文・引用符・文字列境界の検証**
11. **検証済みコマンドと、ユーザーへ提示するコマンド本文が完全に同一であることの確認**

### Phase Aの最終コマンド検証

編集コマンドを作成した後、検証用に別のスクリプトや別のコマンドを作って検証しただけでは、Phase A完了とは判定しない。

必ず、**ユーザーへ実際に提示する最終コマンド本文そのもの**を検証対象として固定する。

特にPythonを含む編集コマンドでは、次を必ず確認する。

- Python全体を `ast.parse` 等で構文検証する。
- Python文字列の開始・終了、引用符、三重引用符、括弧を検証する。
- heredocの開始・終了を検証する。
- シェル側の構文を検証する。
- 編集対象本文とPython文字列の境界を検証する。
- 必要な場合はJavaScript等の生成・編集対象コードについても構文検証する。
- アンカーの件数確認処理が、実際に編集するアンカーと一致していることを確認する。
- 編集コマンドの実行後に必要な検証処理が、実際の変更対象と一致していることを確認する。

**検証後にユーザーへ提示するコマンド本文を変更してはならない。**

検証後に1文字でも変更した場合、そのコマンドは未検証として扱い、Phase Aの最終コマンド検証からやり直す。

検証用に生成した内部変数・内部スクリプト・途中版が構文的に正しくても、最終提示版が同一であることを確認できなければPhase Aは未完了である。

### Phase A完了判定

次のすべてを満たした場合のみ「Phase A完了」と判定する。

- 最新mainを確認した。
- 設計書全文を確認した。
- 第0章を確認した。
- 対象コード・UI・runtime・既存/旧/重複/競合実装を確認した。
- 編集対象と編集方法を最新mainから確定した。
- 編集コマンド作成直前に最新mainとの再照合を行った。
- 編集コマンドそのものを構文検証した。
- 検証対象とユーザーへ提示する最終コマンドが完全に同一であることを確認した。
- 検証後にコマンド本文を変更していない。

1項目でも確認できない場合は「Phase A完了」と言ってはならない。

「検証用スクリプトは通った」「内部で作った原稿は構文的に正しい」「以前のコマンドと同じ」は完了条件にならない。

Phase Aの全項目が揃うまで、実装・編集コマンドを提示してはならない。

Phase Aの途中で、対象0件、対象複数件、構造不一致、旧実装との競合、runtime接続不一致、アンカー不一致、構文検証失敗、最終提示物との不一致などが発生した場合は、過去の確認結果に合わせて進めず、Phase Aの調査へ戻る。

**Phase B：実行・反映・監査**

Phase Aが完了した後だけ、Termuxで実際の変更を行う。

`git pull --ff-only origin main`
→ `編集`
→ `チェック`
→ `git add`
→ `git commit`
→ `git push origin main`
→ `PUSH後の最新GitHub main再取得・監査`

とする。

チェックが失敗しても、チェック失敗だけを理由にPUSHを中止する手順へ変更しない。

Termuxで編集対象・構造・アンカー・構文などが想定と一致しなかった場合は、Phase Bの途中で推測修正を続けず、Phase Aへ戻って現在状態を再調査する。

Phase AとPhase Bを同一視しない。
「確認した」「コマンドを作成した」だけではPhase A完了とは扱わず、「コマンドを提示した」だけではPhase B実行済みとは扱わない。
### 過去確認結果の編集条件への再利用禁止
過去の調査で得られた件数・アンカー・HEAD・blob SHA・コード断片・対象位置・検索結果を、現在の編集条件として固定してはならない。
特に「以前は3件だった」「前回確認したので同じはず」といった過去状態を、現在の対象数や編集可否の根拠にしてはならない。
編集コマンドを作成する直前に確認した最新mainの現在構造だけを、現在の編集対象を確定する根拠とする。

### 編集失敗時の再調査
Termuxで対象件数・構造・アンカー・構文などが想定と一致しなかった場合、過去の確認結果に合わせるための修正や別アンカーの推測を行ってはならない。
その時点の最新ローカル状態を対象として原因を再調査し、必要なら最新mainを再取得して、現在の実コードから編集対象と編集方法を作り直す。
編集失敗後に、失敗した前提を維持したまま別の編集コマンドを連続して提示してはならない。

編集・実装・設計書更新の判断中に、ChatGPTが第0章とは異なる方法を思いついた場合、その方法を第0章より優先してはならない。

まず第0章の既存手順にその判断が含まれているかを確認する。
含まれていない場合は、その独自判断を実行手順へ持ち込まない。

第0章の手順そのものを変更する必要がある場合は、先に第0章へ正式なルールとして統合し、その更新後の手順を基準として以後の作業を行う。

作業中に独自判断を追加してから、後からその判断を正当化するために「安全対策」「検証強化」などとして扱ってはならない。

作業手順を実行する場合の最優先順位は、

`最新main`
→ `設計書全文`
→ `第0章の現行手順`
→ `その手順に従った対象確定`
→ `編集直前の最新main再照合`
→ `Termux実行`
→ `PUSH`
→ `PUSH後の最新main再監査`

とする。

この順序をChatGPT独自の判断で変更してはならない。

編集対象のアンカーは、記憶・推測・過去会話・過去main・断片的な検索結果から再構成してはならない。
編集アンカーは、編集コマンドを作成する直前に確認した最新mainの実コードから、そのまま連続して取得した本文を使用する。
複数行アンカーについて、最新mainに存在する複数の断片をChatGPTが結合したり、空白・改行・インデントを推測して組み立てたりしてはならない。
old = の置換文字列を使用する場合、その文字列全体が編集コマンド作成直前に取得した最新mainの連続本文と完全一致していなければならない。
Termux側ではgit pull --ff-only origin main後に同じアンカーを再検索し、0件なら編集せず再調査、1件なら編集対象確定、2件以上なら文脈と責務を再調査してから編集する。
調査時に存在したアンカーが編集時に存在しない場合、別の文字列へ置換してはならない。最新mainを再取得して実コードからアンカーを取り直す。
編集コマンドのPython構文・引用符・文字列境界も、提示前に成立することを確認し、編集対象本文そのものと編集コマンドの構文を混同しない。

---

### 0.9 既存実装の再利用

新しい処理を追加する前に、同じ目的の現行処理を確認する。

既存処理を利用できる場合は再利用する。

同じ目的の、

- renderer
- manifest
- state
- UI
- runtime入口
- 保存処理
- 再描画処理

を二重実装しない。

既存処理を置き換える場合は、旧入口・旧責務・旧データ経路を実際に追跡し、不要になったものを整理する。

---

### 0.10 runtime確認

機能の実装済み判定は、ファイルや関数の存在だけでは行わない。

必ず実際の経路を確認する。

`UI`
→ `イベント`
→ `ハンドラ`
→ `実処理`
→ `データ更新`
→ `保存`
→ `再描画`

必要に応じて、

`設計書`
→ `対象コード`
→ `呼び出し元`
→ `runtime`
→ `UI`
→ `保存`
→ `再描画`

を双方向に追跡する。

UI文字列が存在するだけ、関数が存在するだけ、renderer APIが存在するだけ、データが存在するだけでは実装済みと判定しない。

---

### 0.11 不整合発見時の処理

最新mainの確認中に不整合を発見した場合、その不整合を意図的に次回作業へ先送りしない。

まず、

1. 実コードを再確認する
2. 同じ原因を特定する
3. 同じ責務に属する関連箇所を洗い出す
4. 実在を確認できた関連不整合をまとめる
5. まとめて修正する
6. 修正した責務と接続先を再確認する
7. 設計書を同じ現在仕様へ統合する

とする。

ただし、実在を確認できない箇所を推測で追加修正してはならない。

---

### 0.12 設計書とコードの同時更新

コードを変更した場合、同じ作業単位で `docs/SIMPLE-OF-IDLE_統合設計書_正本.txt` も現在仕様へ統合する。

設計書だけ変更して実装済みとは判断しない。

コードだけ変更して設計書を後回しにしない。

新仕様は既存の関連仕様へ直接統合する。

古い仕様を履歴として残さない。

同じ仕様を別章へ重複定義しない。

新しい総合設計書、Phase専用設計書、UI専用設計書などの別設計書を作成しない。

---

### 0.13 仕様変更時の全文統合

仕様・用語・分類・名称を変更する場合、対象語句だけを置換して完了としてはならない。

必ず、

`最新main確認`
→ `設計書全文確認`
→ `正式名称・旧名称・同義語・表記揺れ・関連表現を全件抽出`
→ `各箇所の文脈確認`
→ `維持・変更・削除・変更不要へ分類`
→ `既存仕様へ統合`
→ `設計書更新`
→ `更新後全文確認`
→ `旧概念・矛盾・重複確認`
→ `コード・UI・runtime整合確認`

を行う。

単純な全件文字列置換を仕様変更の完了条件にしない。

---

### 0.14 検証失敗とPUSH

検証・チェックの目的は問題箇所を特定することであり、チェック失敗だけを理由に変更全体を破棄・停止してはならない。

PUSH前にチェックや確認を挟んでPUSHを中止する手順にはしない。

必要な変更は、

`編集`
→ `git add`
→ `git commit`
→ `git push origin main`
→ `最新main再取得`
→ `問題箇所確認`
→ `修正`
→ `再PUSH`

の順で進める。

チェック失敗があっても、それだけを理由にPUSHを中止しない。

チェック結果を理由に成功した変更まで無意味に巻き戻さない。

一方、**対象そのものを最新mainから特定できない場合は推測編集を行わない。**

この場合に禁止されるのは「推測編集」であり、ChatGPTが勝手に別の編集方法・別のGitHub書き込み経路へ切り替えることではない。

実際のファイル変更・commit・pushは、常にTermuxで行う。

---

### 0.15 PUSH後の再監査

PUSHしただけでは実装完了と判定しない。

PUSH後は、**最新GitHub `main`そのものを再取得し、設計書だけでなくリポジトリ全体を再帰的・網羅的に確認する。**

確認順序は必ず次とする。

`PUSH結果確認`
→ `最新GitHub main取得`
→ `最新mainのcommit確認`
→ `最新mainのリポジトリtreeを再帰的・網羅的に取得`
→ `全ファイル・全ディレクトリ構成確認`
→ `変更対象ファイル確認`
→ `関連コード確認`
→ `呼び出し元・呼び出し先確認`
→ `UI確認`
→ `runtime経路確認`
→ `データ更新・保存・再描画確認`
→ `旧実装・重複実装・競合実装・旧入口確認`
→ `docs/SIMPLE-OF-IDLE_統合設計書_正本.txt全文再確認`
→ `設計書とリポジトリ全体の整合確認`

「変更したファイルだけ確認した」ことをリポジトリ監査完了とはみなさない。

「関連しそうなファイルだけ確認した」ことをリポジトリ全体確認とはみなさない。

少なくとも最新mainのGit treeを再帰的に取得し、現在存在するファイル・ディレクトリを実在確認したうえで、対象機能に関係するコード・UI・asset・データ・runtime接続を追跡する。

PUSH前に存在しなかったファイル、PUSH前に存在していたファイル、同じ責務を持つ別ファイル、旧入口、重複実装、競合実装についても、最新main上の実在を確認する。

ファイル名・関数名・ディレクトリ構造を過去の会話や過去の確認結果から補完してはならない。

さらに、`docs/SIMPLE-OF-IDLE_統合設計書_正本.txt`についてもPUSH後の最新mainから全文を再取得し、今回のコード変更と設計書が一致していることを確認する。

問題が見つかった場合は、最新main上で実在を確認できた問題箇所だけを修正対象とし、推測による修正は行わない。

PUSH後の**最新main・リポジトリ全体・設計書全文・runtimeの再監査まで**を一つの実装作業単位とする。

### 0.16 実装成功判定

以下だけでは実装成功と判定しない。

- 文字列置換成功
- ファイル変更成功
- 新関数の存在
- HTML文字列の存在
- SVGファイルの存在
- `git diff`の存在
- commit成功
- push成功
- working tree clean

さらに、編集コマンドがエラーなく終了したことだけでも実装成功とは判定しない。

編集コマンドが正常終了した場合でも、PUSH後に最新GitHub mainを再取得し、実際に変更されたコードが意図したコードになっていることを確認する。

対象機能について、

`設計書`
→ `最新mainの実コード`
→ `UI`
→ `イベント`
→ `実処理`
→ `データ更新`
→ `保存`
→ `再描画`
→ `旧実装・重複実装・競合実装が残っていないこと`

の実際の接続が成立していることを確認して初めて実装済みと判定する。

「編集コマンドが成功した」と「実装が成功した」を同一視しない。

「PUSHされた」と「仕様どおり実装された」を同一視しない。

---

### 0.17 作業手順の変更禁止

この章に定めた作業手順を、ChatGPTの判断・ツール制約・API制約・利便性によって勝手に別手順へ変更してはならない。

特に、

- GitHubへ直接書き込む
- ChatGPT側でcommitする
- ChatGPT側でpushする
- Termux作業をGitHub API作業へ置き換える
- 設計書全文確認を省略する
- リポジトリ全体確認を対象ファイル確認へ縮小する
- 推測したアンカーへ置換する
- チェック失敗を理由に設計書で禁止された停止処理を行う
- SH更新スクリプト方式へ変更する

ことを行わない。

必要な実装手段が現在の作業環境で直接実行できない場合は、**設計書の手順を変更せず、Termuxで実行できる正確な操作へ落とし込む。**

---

### 0.18 作業完了条件

SOIの一つの実装作業は、次の全工程を完了して成立する。

`最新main確認`
→ `設計書全文確認`
→ `第0章作業規則確認`
→ `対象仕様確認`
→ `リポジトリ再帰・網羅確認`
→ `関連コード確認`
→ `UI/runtime確認`
→ `既存・旧・重複・競合確認`
→ `変更対象確定`
→ `編集コマンド作成直前に最新実コードを再照合`
→ `編集アンカーの存在数・前後文脈を確認`
→ `推測でないことを確認`
→ `Termux実装`
→ `設計書統合更新`
→ `git add`
→ `git commit`
→ `git push`
→ `GitHub最新main再取得`
→ `PUSH内容再監査`
→ `変更対象が意図した内容になっているか確認`
→ `旧実装・重複実装・競合実装を再確認`
→ `設計書全文再確認`
→ `問題があれば即修正`
→ `再PUSH`
→ `最終runtime確認`

編集コマンドを提示する前に、ChatGPTはそのコマンドが実際の最新mainのコード構造・アンカー・件数と一致していることを確認する。

調査時のコードを記憶だけで編集コマンドへ変換してはならない。

編集コマンドの生成段階で新しい仮定を追加してはならない。

この工程の途中で、ChatGPTが独自判断によって別の作業経路へ変更してはならない。

---

### 0.19 設計書そのものの維持

`docs/SIMPLE-OF-IDLE_統合設計書_正本.txt`には、

- 作業履歴
- 過去の失敗記録
- 過去mainのSHA
- 途中経過
- 確認待ちリスト
- 次回作業予定

を蓄積しない。

設計書は現在採用されている仕様・責務・runtime・データ経路・作業規則を一つに統合した現在仕様書として維持する。

仕様変更時は旧仕様を履歴として残さず、新仕様へ統合する。

同じ仕様・同じ作業規則を複数箇所へ重複記載しない。

エリアごとに敵・素材・装備・ボス・イベント・解禁条件を持つ。通常戦闘エリアは `PHASE4_MAPS` と `ZONES` を0始まりの `zoneIndex` で一対一に対応させ、村周辺・草原・深緑の森・鉱脈洞窟・古代遺跡・魔王領の6エリアを使用する。既存の深緑の森は戦闘データ名「森」を維持し、マップ表示名との差はモンスターID対応で吸収する。洞窟・古代遺跡・魔王領にも敵HP・経験値・ゴールド・戦闘間隔を定義し、選択した地域の通常敵を戦闘・報酬・図鑑へ接続する。マップ選択時は `state.zoneIndex` と `state.phase4.selectedMap` を同期し、前エリアの `state.battleProgress` を0へ戻す。有効な保存済みマップIDがある場合はそのエリアへ `zoneIndex` を同期する。旧セーブに有効なマップIDがない場合は保存済み `zoneIndex` からマップを復元する。プレステージの通常進行リセットでは `village`・`zoneIndex = 0`・`battleProgress = 0` へ同時に戻す。

## 22. 倉庫

素材・資源・装備・発見物などを保存する。

倉庫容量は施設強化で増加する。生産ボーナス適用後の完成品全量が倉庫に収まるかを、レシピ素材を消費した後の仮想在庫で判定する。全量が収まらない場合は素材を消費せず生産を中止する。Phase 3・Phase 7の生産UIは、必要素材が不足している場合は「必要な素材が不足しています。」、素材が足りていて前提施設が不足している場合は必要施設、素材と施設は満たしていて完成品が収まらない場合は「倉庫の空き容量が不足しています。」と理由を優先順位どおりに区別して表示し、製作ボタンを無効化する。共通の `phase3Craft()` でも実行時に素材数・既存の施設条件・容量を再判定する。施設条件と案内文は `phase3RecipeFacilityBlockMessage()` をUIと実処理で共用し、理由は素材不足・施設不足・容量不足の順に優先する。

Phase 7の星鉱石（`starOre`）・エーテル粉（`etherDust`）・星鋼（`starIngot`）・エーテル結晶（`etherCrystal`）・無限断片（`infinityFragment`）・無限核（`infinityCore`）も、既存の資源データと共通倉庫一覧へ接続する。保存・容量計算・表示は既存倉庫処理を利用する。

## 23. 研究

- モンスター
- 生産
- 自動化
- 探索
- 拠点
- 技術
- 未知領域

研究には素材・時間・条件などを設定する。

研究進行速度は、既存のPhase 6/7共通研究倍率に、Phase 5のペット効果・選択中称号効果・取得済み実績報酬の `research` を加算して算出する。Phase 7研究も既存の研究進行経路を使い、この倍率は一度だけ適用する。

未知エリアの発見率は、既存のPhase 6/7共通発見倍率に、Phase 5のペット効果・選択中称号効果・取得済み実績報酬の `discovery` を加算した後、既存の確率上限を適用する。

研究完了時と未知エリア発見時は、既存Phase 5 rendererを通じて図鑑・実績・称号・コレクションボーナスを再評価する。専用の重複更新経路は追加しない。

Phase 5の研究系実績・称号が参照する完了研究数は、Phase 4の `state.phase4.researchLevels` とPhase 7の `state.phase7.completedResearch` を合算する。

## 26. モンスター図鑑

遭遇・撃破したモンスターを記録する。

記録：

- 名前
- 出現場所
- レベル
- ドロップ
- 撃破数
- 初回撃破
- レア情報

通常エリアの敵IDは、スライム（`slime`）、ゴブリン（`goblin`）、ウルフ（`wolf`）、洞窟ゴブリン（`cave-goblin`）、遺跡守衛（`ruins-guard`）、魔族兵（`demon-soldier`）とする。洞窟の守護者（`cave-guardian`）、古代遺跡の守護者（`ruins-guardian`）、魔王領の支配者（`demon-lord`）はボス用IDを維持し、通常エリアの撃破をボスの撃破数へ加算しない。`ZONES[state.zoneIndex].name` から通常敵IDを一意に選び、すべての通常討伐はそのIDへ記録する。Phase 4の `state.phase4.defeatedBosses` とPhase 7のボス撃破記録は既存のモンスター図鑑へ連携し、既に保存済みの撃破記録もロード時に一度だけ図鑑へ反映する。旧ID `ancient-guardian` は、実際の `ruins-guardian` 撃破記録がある場合だけ新IDへ移行し、旧IDに残っていた通常戦闘の誤集計をボス撃破数として引き継がない。

## 27. 装備図鑑

入手した装備を記録する。

登録済み装備はコレクションとして保持する。入手数は名前ごとに集計するが、加算判定には装備インスタンスの固有IDを使用し、同一インスタンスを重複登録しない。

旧セーブに固有IDの登録履歴がない場合は、移行時に所持装備を照合して追跡情報を作る。過去の正確な入手総数は復元できないため、既存レコードは登録済みなら最低1個を保持し、現在所持している個数を反映する。移行後は新しい固有IDが初めて確認されたときだけ入手数を加算する。

## 31. 実績

例：

- 初戦闘
- 100体撃破

- 10回転生

取得済み実績の各 `reward` は、共通の実績効果集計で報酬キーごとに合算し、一度だけ既存処理へ適用する。`attack` は `adventurerStats()` の攻撃力、`exploration` は冒険者速度、`production` は既存 `phase3Craft()` の非装備レシピ出力、`research` と `discovery` は既存Phase 4の研究進行と未知エリア発見率、`collection` は `collectionBonus` に接続する。従来の基礎加算である取得済み実績数×0.003を維持し、取得済み実績の `reward.collection` 合計を別途加算した後、上限0.25を適用する。攻撃力報酬は個別冒険者の恒久攻撃力フィールドへ重ねて加算しない。

実績「初製作」は、既存 `phase3Craft()` の成功完了回数 `state.phase3.craftsCompleted` を参照し、装備・非装備およびPhase 7レシピを1回ずつ数える。

## 47. 最重要ルール

Simple-Of-Idleでは、
「大量の要素があること」だけを目的にしない。

必ず、

獲得
→ 使用
→ 強化
→ 解禁
→ 新しい獲得
→ 新しい使用
→ 新しい成長

という接続を作る。

新システムを追加するときは、
既存システムとの入力・出力・成長・解禁・プレステージの関係を定義する。

孤立したシステムを増やさない。

この原則をSimple-Of-Idleの全実装に適用する。

## 48. Phase 1〜7統合ルール

Phase 7で追加される新世界・新職業・新素材・新装備・新モンスター・新ダンジョン・新ボスは、
既存Phase 1〜6のシステムから独立した別系統として扱わない。

### 統合

- 新職業は既存の職業レジストリへ登録する。
- 新素材は既存の資源・素材図鑑へ登録する。

### Phase 6恒久効果の接続先

Phase 6の恒久効果は、表示だけに留めず既存Phase 1〜7の処理へ接続する。

未知エリア発見時は `phase4DiscoverUnknown()` から `phase4RefreshPhase5Progress()` を経由して既存 `phase5Render()` を呼び出す。`phase5Render()` は `phase5RegisterAllExisting()` を通じて `phase5RegisterDiscoveries()`、実績・称号の再評価、コレクションボーナス更新を行う。

これにより、

探索
↓
ランダムイベント
↓
未知エリア発見
↓
Phase 4報酬
↓
Phase 5発見図鑑
↓
発見恒久効果
↓
Phase 7発見補正

という既存システム間の循環を維持する。

## 60. Phase 5/6/7生産補正の適用範囲統一

Phase 5の取得済み実績・ペット・称号の生産効果、Phase 6の恒久ツリー効果、Phase 7職業・恒久成長の生産効果は、既存の資源獲得全体へ無差別に適用せず、既存Phase 3の非装備レシピ出力へ接続する。

`phase7ProductionMultiplier()`（Phase 5実績・ペット/称号効果、Phase 6生産効果、Phase 7職業効果・恒久効果を合算）
↓
既存 `phase3Craft()`
↓
非装備レシピの資源出力
↓
既存 `phase3AddResource()`
↓
既存倉庫・素材図鑑・生産記録
`state.phase3.produced` には倉庫へ全量を追加できた補正適用後の出力量だけを記録し、倉庫在庫と生産記録の不一致を生じさせない。

採取、戦闘報酬、ダンジョン報酬、ボス報酬、ランダムイベント報酬、Phase 7新世界の放置報酬など、単純な資源獲得経路には生産補正を適用しない。

装備製作については既存 `phase3Craft()` の装備生成処理をそのまま利用し、生産補正によって装備を複製したり、装備出力を倍率処理したりしない。

Phase 5/6/7専用の独立した生産処理は追加せず、既存Phase 3のクラフト処理をラップして補正を接続する。

これにより、採取・戦闘・探索報酬は通常の資源獲得経路を維持し、生産・クラフトの非装備レシピ出力だけに統合生産補正を適用する。

## 61. Phase 7職業定義の一元化

Phase 7職業の実能力・表示名・説明・アイコン・研究・生産・探索・発見効果は `PHASE7_JOB_REGISTRY` を正本とする。

`PHASE7_JOBS` は世界との対応およびPhase 7職業一覧・解禁管理に必要な最小メタデータだけを保持する。

職業効果の計算は `PHASE7_JOB_REGISTRY` から取得し、別の職業効果定義を持たない。

既存 `JOBS` への登録も `PHASE7_JOB_REGISTRY` を使用する。

これにより、同一職業について複数箇所に能力値を定義して不一致が発生することを防止する。

職業の実能力を変更する場合は `PHASE7_JOB_REGISTRY` の変更だけで既存ステータス計算とPhase 7固有効果へ反映される。



## 62. セーブデータの耐久性と復旧

Simple-Of-Idleの通常セーブは既存の `localStorage` を継続利用する。

### 通常保存

- 現行セーブキーは `simple-of-idle-save-v2` を使用する。
- 状態変更時の既存保存処理を維持する。
- オンライン進行中は既存の10秒周期保存を維持する。
- 画面非表示・ページ終了時にも既存保存処理を実行する。

### バックアップ

現行セーブとは別に `simple-of-idle-save-v2-backup` を保持する。

通常保存では、現行の正常な `v2` セーブを次回保存前にバックアップへ移し、
保存途中の破損などで現行セーブを読み込めない場合にバックアップから復旧する。

バックアップから復旧した場合は、その復旧済みデータを次回保存時に現行セーブとバックアップへ同期し、
破損した現行データをバックアップへ再保存しない。

### 復旧優先順

1. 現行 `v2`
2. `v2` バックアップ
3. 旧 `v1` セーブの移行
4. 初期状態

現行 `v2` のJSONが破損していても、バックアップが正常なら初期状態へ直接戻さない。

### セーブ書き出し・読み込み

ユーザーがゲーム内から現在のセーブをJSONファイルとして書き出せるようにする。

セーブ読み込みの表示ボタンは、実際のファイル選択入力へ接続し、表示上存在するだけの未接続ボタンを残さない。

書き出したセーブはブラウザ外へ保持できるため、
ブラウザのサイトデータ削除・端末変更・ブラウザ変更などで `localStorage` が失われた場合も、
ユーザーがファイルを読み込むことでゲーム状態を復元できる。

読み込み時は保存データの形式を検証し、正常なデータだけを現行v2セーブとして登録する。現行v2・v2バックアップ・旧v1の保存領域は一つのトランザクションとして扱い、保存後の通知や再読み込み開始までに失敗した場合は変更前の値へ復元する。復元に失敗したキーがあれば、そのキー名と復元エラーを共通エラーモーダルへ通知し、成功扱いにしない。

### リセット

「セーブリセット」は、

- 現行v2セーブ
- v2バックアップ
- 旧v1セーブ

を削除して初期状態から開始する。

通常のゲーム進行中に自動的にリセットを行わない。

### 旧セーブ削除

旧v1セーブは現行v2セーブと分離して保持する。

「旧v1削除」操作では `simple-of-idle-save-v1` のみを削除し、
現行v2セーブおよびv2バックアップには影響させない。



### 起動時オフライン処理のロード順序

`game.js` が最初にロードされる構成を維持する。`game.js` はセーブ復元直後に初回オフライン用の経過秒数を記録するが、戦闘進行は後段Phaseの戦闘ラッパーが登録されるまで実行しない。

処理順序：

ゲーム起動
↓
`game.js` がセーブを復元し、起動時未処理秒数を記録
↓
Phase 3・4・5・6・7をロードし、戦闘報酬・恒久効果・図鑑/実績/称号ラッパーを登録
↓
Phase 3の `state.phase3.lastProcessedAt` を基準に採取進行を処理
↓
Phase 4の `state.phase4.lastProcessedAt` を基準に研究・遠征・イベントを処理
↓
Phase 7研究・ダンジョン・ボスは既存 `phase4ProcessResearch()` / `phase4ProcessActivity()` 経由で進行
↓
Phase 7新世界素材は `phase4ProcessOffline()` から既存 `phase3AddResource()` へ渡す
↓
全スクリプトの `load` 完了後、`game.js` が記録済みの経過秒数で初回戦闘オフライン処理を実行
↓
各討伐が `processBattle()` を通り、戦闘報酬とPhase 3〜5の討伐連動処理を更新
↓
共通UI再描画・保存・オフライン報告表示・通常戦闘タイマー開始

Phase 7が独自のオフライン時計や起動時時間の別引き渡し経路を持つことは禁止する。Phase 7の研究・活動・新世界素材は、既存Phase 4のオフライン処理経路から各一回だけ進める。Phase 3・4の処理時刻は効果系とPhase 7接続が登録される前に更新しない。

これにより、

通常プレイ
↓
v2自動保存
↓
v2バックアップ
↓
破損時バックアップ復旧
↓
必要に応じてJSON書き出し
↓
サイトデータ削除後にJSON読み込み
↓
ゲーム状態復元

という保存・復旧経路を成立させる。

保存データは既存の全Phase状態を含む単一の `state` を基準とし、
Phase 7だけの別保存領域や別セーブシステムを追加しない。

## 63. 共通エラー処理

ゲーム全体の予期しない例外・未処理Promise例外・主要な失敗処理は、共通エラーハンドラへ集約する。

### 基本経路

既存ゲーム処理
↓
例外・失敗
↓
`SimpleIdleErrorHandler`
↓
共通エラーモーダル
↓
エラー内容・発生画面・実行中処理・発生元・スタックを表示
↓
ログコピー / 再試行 / ページ再読み込み

### 対象

- `window.error`
- `unhandledrejection`
- `runErrorSafeOperation(phase, operation, file, callback)` を通るゲーム操作（冒険者選択・転職・スキル・施設・装備・雇用・採取・製作・探索・研究・コレクション・プレステージ・新世界）、保存操作（手動保存・書き出し・読み込み・リセット・旧v1削除）、タブ切替、画面再描画、Phase 3〜7の初期化、定期タイマー、表示状態変更、終了時保存
- セーブ処理など、既存処理側で捕捉している重大な失敗処理
- ファイル読み込みのような非同期イベントは、Promiseの成否まで発生元・処理名・再試行先を保持する

`runErrorSafeOperation()` は各処理の開始時点で `state`、`lastTick`、`saveTimer`、`recoveredFromBackup` および `SAVE_KEY`・`SAVE_BACKUP_KEY`・`LEGACY_SAVE_KEY` の生データをスナップショットとして保持し、同期例外・Promise拒否時には `createErrorSafeRetry()` を通じてメモリ状態・進行時計・保存領域を復元し、同じ処理の再試行先をモーダルへ渡す。保存領域の復元で失敗したキーがあれば、元の例外と失敗したキーを共通モーダルへ通知する。非同期操作とその再試行には共通の `errorSafeOperationPending` ロックを使用する。非同期処理が完了するまでは他の共通ラッパー操作・定期処理を受け付けず、処理コンテキストと再試行先が上書きされることを防ぐ。エラーモーダル表示中、通常操作と定期処理は既存の再試行先を置き換えない。エラーモーダルの「閉じる」は、表示を閉じると同時に前回操作のコンテキストと再試行先を解除し、後続の別エラーに古い再試行先が残ることを防ぐ。再試行ボタンは実行対象を先に取得してからモーダルを閉じるため、再試行処理の成否が確定するまでは元の操作情報を保持する。Phase 3〜7の初期化ラッパーは `retryPageReloadOnModal` を指定する。該当する初期化処理が失敗した直後、または先行Phaseのエラー表示中に後続Phaseの初期化がスキップされる場合は、再試行先をページ全体の再読み込みに設定し、Phase 7の初期化失敗も含めて `game.js` からPhase 7までの初期化順序を最初からやり直す。非同期操作のロックは、成功時の処理コンテキスト・再試行先の解除、または失敗時の状態復元・エラー報告・初期化時の再読み込み先設定が完了してから解除する。再試行ボタンはPromiseの成否を待ち、成功時だけ処理コンテキストと再試行先を解除する。セーブ読み込みはファイル読み込み・検証・保存を一つの非同期操作として扱い、失敗時は元のセーブ領域を復元してモーダルへ通知する。成功時だけ処理コンテキストと再試行先を解除する。定期処理はエラーモーダル表示中および非同期操作中に停止し、失敗した処理の再試行先を別処理で上書きしない。同一エラーの重複報告は表示中のモーダル内でのみ抑制し、モーダルを閉じて再試行した処理が同じエラーで再び失敗した場合は、抑制せずモーダルを再表示する。

既存処理でエラーを捕捉する場合も、ゲーム状態を勝手に初期化せず、共通ハンドラへ通知する。

### 責務

共通エラーハンドラは、エラーの表示・記録・再試行導線だけを担当する。ゲーム状態のスナップショットと処理の実行・復元は `game.js` の `runErrorSafeOperation()` に一元化し、再試行先は同関数から `setRetry()` で登録する。ハンドラ独自の処理実行ラッパーを公開しない。

以下を独立管理してはならない。

- ゲーム状態
- Phase 1〜7の進行
- セーブデータ
- オフライン進行
- 独立したゲームタイマー
- 独立した報酬・成長

既存のゲーム処理経路を変更せず、異常発生時の可視化と復旧導線だけを追加する。

### 再試行時の状態整合性

状態変更を含む操作の再試行では、操作開始前の単一の `state` スナップショットを基準にする。

- 操作開始時に `state`、`lastTick`、`saveTimer`、`recoveredFromBackup` と3つのセーブキーの生データを退避し、失敗時は開始前へ復元する。
- 操作途中で例外が発生した場合は、退避した状態へ戻してからエラーを通知する。
- エラーモーダルの「再試行」は、退避状態から操作全体を一度だけ再実行する。
- 保存や描画など後段で失敗した場合も、途中まで行われた状態変更を残したまま同じ操作を二重実行しない。
- セーブ時刻 `lastSavedAt` は保存成功時に確定し、保存失敗時には次回オフライン計算の基準時刻を先へ進めない。
- この状態スナップショットはゲーム処理側が管理し、`SimpleIdleErrorHandler` 自体にはゲーム状態を持たせない。
- 再試行が成功した場合は通常の成功経路へ戻り、古い再試行状態を残さない。

これにより、

操作開始前の状態
↓
状態変更を伴う操作
↓
途中で失敗
↓
開始前の状態へ復元
↓
エラー表示
↓
再試行
↓
同じ操作を一度だけ再実行

という復旧経路を成立させる。

### UI

既存の `offlineModal` などのゲーム用モーダルとID・CSS名前空間を分離する。

モーダルには、少なくとも以下を表示する。

- エラー種別
- 発生画面
- 実行中の処理
- 発生元ファイル
- エラー内容
- スタックトレース

操作は、閉じる・現在の処理を再試行・ページ再読み込み・エラーログコピーを提供する。

## 64. SOI固有の事後監査・正本設計書の維持

本章は第0章の作業プロトコルを補完するSOI固有の監査・設計書維持要件を定める。作業順序、Phase A／Phase B、編集アンカー、Termux操作、commit・PUSH、一般的なPUSH後監査は第0章を唯一の基準とし、本章で重複定義しない。

### PUSH後のSOI固有監査

PUSH後は最新GitHub `main`を再取得し、正本設計書と、今回の変更に関係するPhase 1〜7の実装を照合する。

対象機能だけでなく、実際に接続している以下の経路を確認する。

- 状態管理・レジストリ・共通計算処理
- UI・イベント・ハンドラ・実処理
- 報酬・資源・成長・解禁の更新
- セーブ・復元・オフライン進行
- 保存後の再描画と画面遷移
- 同じ責務を持つ旧実装・重複実装・競合実装・旧入口

問題が見つかった場合は、最新main上で実在を確認できた問題と、同じ原因から発生している関連問題をまとめて修正する。無関係な機能を巻き込まず、修正後は最新mainを再取得して同じ経路を再監査する。

設計書に記載されていること、関数が存在すること、画面に文字列が表示されることだけでは「実装済み」と判定しない。UIから実処理、状態更新、保存、再描画まで接続していることを確認する。

### 正本設計書の一元管理

`docs/SIMPLE-OF-IDLE_統合設計書_正本.txt` をSOIの現在仕様を定義する唯一の正本とする。

新仕様・変更仕様・廃止仕様は、既存の関連箇所を確認して現在仕様へ統合する。単純に末尾へ追記して古い仕様と新しい仕様を併存させない。仕様の重複、矛盾、旧名称、廃止された処理経路を整理し、複数章に同じ仕様を独立して定義しない。

コードを変更した作業では、同じ作業単位で正本設計書も更新する。設計書だけを更新して実装済みと判断せず、コードだけを変更して設計書更新を後回しにしない。別の総合設計書やPhase専用設計書を作って仕様の二重管理を行わない。

仕様変更後は、更新された正本設計書の全文を再確認し、関連するPhase間の接続、名称、現在仕様、旧仕様の残存を確認する。

### 最終完了条件

SOIの作業完了は、PUSH後の最新mainを基準に、正本設計書全文、関連コード、UI、runtime経路、データ更新、保存・復元、オフライン処理、再描画、旧・重複・競合実装を確認し、見つかった関連問題を修正して再PUSHした状態とする。
